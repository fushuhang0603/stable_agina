## 1. 需求到架构的约束提取

从《需求》中提取出对后端架构有强制影响的约束，后续每一处设计都必须能回溯到这里。

| 编号 | 需求来源 | 约束内容 | 架构落点 | 判定 |
|---|---|---|---|---|
| C1 | 《需求》§3、§6 权限安全 | 患者/医生/管理员三类角色，医生只能看"分配给自己"的患者 | RBAC 菜单权限 + 行级数据权限拦截 | ✅ 必须实现 |
| C2 | 《需求》§6 文件安全 | MinIO 文件不得裸链接访问 | 后端鉴权 + 短时预签名 URL | ✅ 必须实现 |
| C3 | 《需求》§7.1~7.5 | AI 五层约束：提示词/参数/流程/数据绑定/日志 | AI 集成服务独立为唯一出口 | ✅ 核心亮点 |
| C4 | 《需求》§7.3 | AI 输出仅为草稿，人工审核后才可归档、才对患者可见 | 摘要 + 工单双状态机 | ✅ 必须实现 |
| C5 | 《需求》§6 容错性 | 大模型超时/失败时原始数据不丢失，可重试 | 数据集先落库再调模型 | ✅ 必须实现 |
| C6 | 《需求》§5.3.2 | 到达随访周期自动创建工单 | 定时任务 + 周期配置 | ✅ 必须实现 |
| C7 | 《需求》§5.1 | 操作日志、AI 调用日志可查、不可由业务端删除 | AOP 操作日志 + 只读日志表 | ✅ 必须实现 |
| C8 | 《需求》§6 数据隐私 | 患者敏感信息脱敏展示 | 序列化层脱敏注解 | ⚠️ 简化实现即可 |
| C9 | 《需求》§4.5、§6 兼容性 | 患者端一套代码可打包 H5 / 小程序 | 本期只做 H5（你的决定） | ⚠️ 与原文差异，见 §15 |
| C10 | 《需求》§5.3.2、§5.3.5 | 随访报告 PDF 导出、报表导出 | 后端 OpenPDF 生成 | ⚠️ 可降级为前端打印 |

**架构层面的关键结论**：本系统的技术重心不在业务 CRUD，而在 **C1（行级权限）与 C3/C4（AI 受控生成）** 这两条主线上。因此架构设计把"数据权限"和"AI 集成"做成两个横切基础设施，其他业务模块只是它的使用方。

## 2. 架构风格决策

| 方案 | 说明 | 结论 |
|---|---|---|
| 微服务（Spring Cloud） | 认证、业务、AI、文件拆成独立服务 | ❌ 单机 2C4G 部署、单人开发、无服务治理需求，纯增负担，答辩也难讲清价值 |
| 单体分层 | 一个 Spring Boot 应用，按业务域分包，内部单向依赖 | ✅ 采纳 |
| 前后端分离 | H5 端 + Web 端分别独立部署，统一 `/api` 契约 | ✅ 采纳（这是《需求》§4 已定的） |

**最终架构风格：前后端分离的"模块化单体"（Modular Monolith）**

- 部署上是 **1 个聚合 jar**（4 个 Maven 模块由 `sa-admin` 聚合打包）+ MySQL + Redis + MinIO，Nginx 做静态资源与反向代理；
- 代码上按业务域分包，域内高内聚，跨域只允许通过 Service 接口调用，禁止 Controller 互相调用；**模块间依赖单向**（`sa-admin → sa-business → sa-system → sa-common`），编译器即约束，比单纯靠包名约定更硬；
- 预留拆分点：`sa-business` 内的 `ai`、`file` 子包对外只暴露接口，将来若要拆服务，直接抽成独立 Maven 模块即可（论文里可作为"可演进性"论述）。

### 5.2 模块职责与依赖方向

| 模块 | 职责 | 依赖 |
|---|---|---|
| `sa-common` | `Result` / `ErrorCodes` / `PageResult` / `BizException` / `GlobalExceptionHandler` / `BaseEntity` / 枚举 / 工具类 / 脱敏注解 / `@OperationLog` + AOP / Redis 与 Jackson 配置 | 无业务依赖；`starter-web`、`validation`、`aop`、`data-redis`、`mybatis-plus`、`springdoc`、`lombok`、`hutool` |
| `sa-system` | 用户/角色/菜单/字典/参数/操作日志 CRUD；`SecurityConfig`、`JwtTokenProvider`、`JwtAuthenticationFilter`、`LoginUser`、`DataScopeContext`、`DataScopeInterceptor`、`MybatisPlusConfig` | `sa-common` + `spring-boot-starter-security` + `jjwt` |
| `sa-business` | 八大业务域：`patient` / `monitor` / `medication` / `followup` / `ai` / `file` / `notice` / `stats`，外加 `job` 调度 | `sa-system`（用行级权限上下文与当前登录人） |
| `sa-admin` | **不含业务代码**：`StableAnginaApplication`、`application*.yml`、`db/migration/V*.sql`、`MinioConfig` / `OpenApiConfig` / `AsyncConfig` | `sa-business`（传递依赖 `sa-system`、`sa-common`）+ `flyway-core`、`flyway-mysql` |

```
sa-admin → sa-business → sa-system → sa-common      （只允许向右依赖，禁止反向引用）
```

> 与急救系统一致：`sa-admin` 是唯一的 `spring-boot-maven-plugin`（`repackage`）打包目标，`mainClass = com.stable.angina.StableAnginaApplication`，其余模块 `packaging=jar` 且不引入打包插件。

### 5.3 各模块包结构（标注功能分层）

**`sa-common`** —— 公共层，任何业务都可安全引用：

```
com.stable.angina.common
├── api/          Result、ErrorCodes、PageResult
├── exception/    BizException、GlobalExceptionHandler
├── entity/       BaseEntity（id / create_by / create_time / update_by / update_time / deleted）
├── enums/        角色、工单状态、摘要状态、打卡状态、风险等级
├── util/         日期、脱敏、雪花 ID / 序列号
├── sensitive/    脱敏注解 + Jackson 序列化器（C8）
├── log/          @OperationLog 注解 + OperationLogAspect + 日志实体/Mapper（C7）
└── config/       RedisConfig（序列化）、JacksonConfig
```

**`sa-system`** —— 安全层 + 系统管理业务层：

```
com.stable.angina.system
├── config/       SecurityConfig（过滤器链/白名单/方法级鉴权）
│                 MybatisPlusConfig（分页插件 + DataScopeInterceptor 注册）
├── security/     JwtTokenProvider、JwtAuthenticationFilter、LoginUser
│                 UserDetailsServiceImpl、DataScope、DataScopeContext、DataScopeInterceptor
├── controller/admin/   AuthController、UserController、RoleController、MenuController
│                       DictController、ConfigController、OperLogController
├── service/  service/impl/  mapper/
└── entity/       SysUser、SysRole、SysMenu、SysDict、SysConfig、SysOperLog
```

> Controller 严格按端分包：`controller/admin/**` 供医生端与管理员端使用，业务端接口放 `sa-business/{domain}/controller/client/**`。与急救系统 `controller/admin` + `controller/client` 的做法一致。

**`sa-business`** —— 业务层，按域内聚，每个域内部统一分层：

```
com.stable.angina.business
├── patient/      【档案】档案 / 基线 / 变更留痕 / 医患归属
├── monitor/      【监测】发作打卡 / 血压 / 服药打卡 / 不良反应
├── medication/   【医嘱】用药医嘱
├── followup/     【随访】工单 / 问卷 / 归档记录
├── ai/           【AI 集成，唯一出口】
│   ├── client/       LlmClient 接口 + SpringAiLlmClient 实现（Mock 实现由 ai.mock 切换）
│   ├── prompt/       提示词模板装配（版本化，只读）
│   ├── collector/    数据集采集器（跨 monitor/medication 只读）
│   ├── validator/    六段结构校验器
│   ├── service/      AiSummaryService、AiCallLogService、SummaryGenerator
```

## 6. 认证、RBAC 与行级数据权限（核心难点 1）

### 6.1 令牌方案

| 项 | 设计 |
|---|---|
| 登录 | 账号密码 → BCrypt 校验 → 签发 JWT（含 userId、username、roleCodes） |
| Access Token | 有效期 2 小时，放 `Authorization: Bearer xxx` |
| 续期 | 每次请求命中 Redis 白名单则滑动续期（《需求》"token 自动续期"） |
| 登出 | 删除 Redis 白名单 key，令牌立即失效（《需求》"登出销毁 token"） |
| Redis Key | `auth:token:{userId}:{jti}` → 登录信息，TTL 同令牌 |
| 并发登录 | 允许，但记录 login_log（《需求》操作日志） |

为什么不用"纯无状态 JWT"：需求明确要求"登出失效"，无状态令牌做不到即时失效，加 Redis 白名单是最小代价方案。

### 6.2 权限模型

```
sys_user ──< sys_user_role >── sys_role ──< sys_role_menu >── sys_menu
                                     │
                                     └── data_scope（ALL / ASSIGNED_PATIENTS / SELF）
patient  ──< doctor_patient >── sys_user(医生)
```

- **菜单权限**：`sys_menu` 存 `permission` 标识（如 `followup:summary:generate`），接口上用 `@PreAuthorize("hasAuthority('xxx')")`。
- **行级数据权限**：医生角色 `data_scope = ASSIGNED_PATIENTS`，通过 `doctor_patient` 关系表限定可见患者集合。

### 6.3 行级权限实现（关键设计）

采用 **MyBatis-Plus `InnerInterceptor` 改写 SQL**，而不是在每个 Mapper 手写 `and doctor_id = ?`（《开题报告》难点 2 明确要求避免手工拼接）。

```text
请求进入
  └─ JwtAuthenticationFilter 解析令牌 → 得到 LoginUser
       └─ DataScopeContext 写入 ThreadLocal（角色 + 数据范围 + userId + 可访问 patientId 集合）
            └─ DataScopeInterceptor.beforeQuery：解析 SQL 的 from/join 表
                 ├─ 命中受控表（patient / angina_attack / blood_pressure /
                 │   medication_advice / medication_checkin / adverse_reaction /
                 │   followup_ticket / followup_record / ai_summary / file_info）
                 │      ├─ 医生：注入 patient_id IN (select patient_id from doctor_patient where doctor_id = ?)
                 │      └─ 患者：注入 patient_id = 当前登录患者ID
                 └─ 管理员：不注入（ALL）
请求结束 → 清理 ThreadLocal（filter finally 中 remove，防线程池串数据）
```

补充规则（必须写清，否则会出现"统计口径错误"）：

1. **统计类 SQL**：只对明细查询注入条件，聚合 SQL 通过 `@DataScopeIgnore` 注解显式跳过，并在 Service 层手工限定范围；
2. **多表关联**：以主表 `patient_id` 为准注入，别名统一约定；
3. **写操作**：INSERT/UPDATE 不做 SQL 改写，改为在 Service 层做"归属校验"（`assertPatientAccessible(patientId)`），避免 UPDATE 被改写导致误伤；
4. **患者端**：患者 ID 一律从令牌取，不信任前端传参（防越权）。

> 论文表述建议：本节作为"权限设计"章节，配一张"过滤器链 → 拦截器 → SQL 改写"的时序图，并给出越权测试用例（医生 A 访问医生 B 患者返回 403）。

### 7.5 六段输出结构（固定，不可增删）

`basic_info`（基本信息）、`angina_attack`（心绞痛发作情况）、`blood_pressure`（血压波动）、`medication_adherence`（用药依从性）、`problems`（存在问题）、`assessment`（初步评估）。

### 7.6 大模型接入方式（Spring AI 1.1.x + DeepSeek）

**总体**：用 Spring AI 的 OpenAI Starter 接 DeepSeek（DeepSeek 提供 OpenAI 兼容协议），所有模型调用收敛到 `LlmClient` 一个出口，业务代码不出现任何 HTTP 细节。

- **依赖**：`spring-ai-bom:1.1.x` + `spring-ai-starter-model-openai`，版本由 BOM 统一管理，与 Spring Boot 3.5.x 配套；
- **模型工厂**：`LlmModelFactory` 不走配置文件静态配置，而是在运行时从 `sys_config` 读取 `ai.base-url` / `ai.api-key` / `ai.model`，用 `OpenAiApi.builder()` + `OpenAiChatOptions` 构建 `OpenAiChatModel` 并缓存；管理员改参数后只清缓存，不需要重启（满足《需求》"接口地址、密钥由管理员配置，不硬编码"）；
- **调用方式**：`LlmClient` 内部持有 `ChatClient`（`ChatClient.builder(chatModel)`），一次调用 = `prompt 渲染 → ChatClient.prompt().options(...).call().content()`；
- **参数约束落点**（§7.2 第二层）：`ChatOptions` 固定 `temperature=0.2`、`topP=0.8`、`maxTokens=1200`，全部来自 `sys_config`，不在代码里写死；
- **DeepSeek 参考配置**：`base-url = https://api.deepseek.com`，`model = deepseek-chat`，`completions-path = /v1/chat/completions`（具体以管理员配置为准，切换通义/智谱/本地 Ollama 只需改 base-url + model，代码零改动）；
- **密钥安全**：API Key 在 `sys_config` 中 **AES 加密存储**，`LlmModelFactory` 构建时解密，日志中一律打印掩码（`sk-****abcd`）；
- **超时与重试**：Spring AI 底层 `RestClient`/`WebClient` 设置连接超时 10s、读取超时 120s；仅对网络类异常（`ResourceAccessException`）重试 1 次，**结构不合规不自动重试**，直接置 `FAILED` 交医生决定（防止无限烧 token）；
- **降级与可追溯**：每次调用把请求模型、耗时、token 用量、原始响应、异常写 `ai_call_log`；数据集在调用前已落 `ai_call_log.dataset_json`（C5），失败可原样重生成；
- **生成方式**：同步接口 + 前端 loading（毕设场景足够）；异步化时只需改为任务表 + 轮询，不影响 `LlmClient` 以上任何一层。

## 8. 文件服务设计（MinIO）

```text
上传：H5/Web → 后端 /api/files/upload → 校验类型大小 → MinIO 私有桶
      → file_info 落库（biz_type, biz_id, object_key, size, sha256, uploader）

      → 生成 5 分钟预签名 URL 返回 → 前端直接 GET（不暴露永久裸链接）
```

- 桶策略：**private**，禁止匿名读（《需求》§6 文件安全）；

- 附件归属校验复用 §6.3 的 `assertPatientAccessible`。

## 11. 接口规范与 API 清单

### 11.1 统一约定

```
完整路径 = context-path(/stableanginaapi) + 接口路径(/api/{module}/{resource})
GET/POST/PUT/DELETE  /api/{module}/{resource}
请求头：Authorization: Bearer <token>
成功响应：{ "code": 0, "message": "ok", "data": {...} }
失败响应：{ "code": 1003, "message": "用户名或密码错误", "data": null }
分页请求：{ page, size }        分页响应：{ total, page, size, pages, records }
错误码：0 成功；-1 通用失败；401 未登录；403 无权限；400 参数错误；
       1001 用户禁用；1002 用户不存在；1003 凭证错误；1004 用户名已存在；1005 手机号已存在；
       500 系统异常；6001 AI 调用失败（见 ErrorCodes 常量类，禁止散落魔法数字）
```

> 对齐急救系统：`Result{code,message,data}` 不带 `traceId`（追踪靠日志 `MDC`）；`PageResult{total,page,size,pages,records}`；`ErrorCodes` 集中定义常量；`GlobalExceptionHandler` 分类型兜底（`BizException` / 参数校验 / 401 / 403 / 400 / 500）。

## 12. 统一技术规范

| 规范 | 做法 |
|---|---|
| 统一响应 | `Result<T>` + `ErrorCodes` + `PageResult<T>` + `GlobalExceptionHandler`（见 §11.1） |
| 参数校验 | `@Validated` + JSR-303；业务校验在 Service 抛 `BizException` |
| 操作日志 | 自定义 `@OperationLog(module, action)` + AOP 异步写入 `sys_oper_log`（《需求》§5.1） |
| 敏感脱敏 | 自定义 `@Sensitive(SensitiveType.PHONE/NAME)` + Jackson 序列化器 |
| 逻辑删除 | `BaseEntity.deleted` + MyBatis-Plus 逻辑删除 |
| 时间 | 统一 `LocalDateTime`，`yyyy-MM-dd HH:mm:ss`，时区 Asia/Shanghai |
| 审计字段 | `create_by/create_time/update_by/update_time` 由 `MetaObjectHandler` 自动填充 |
| 事务 | 只在 Service 层加 `@Transactional`；AI 调用不放事务内（避免长事务占连接） |
| AI 相关 | 先落库数据集 → 再调模型 → 再更新状态，三步分离，保证 C5 容错 |
| 配置管理 | 仅保留 `application-local.yml` / `application-prod.yml` 两份自包含配置（各自包含公共项 + 环境差异）；配置项直接写固定值、不使用 `${}` 占位符，部署时可用同名环境变量覆盖 |
| 数据库变更 | 一律新增 Flyway `V{n}__xxx.sql`，禁止手改已执行脚本（见 §5.4） |
| Controller 分包 | `controller/admin/**`（医生/管理员端）、`controller/client/**`（患者端），不混放 |

## 13. 部署架构

```uml
@startuml
title 单机部署架构（Linux 2C4G）
skinparam backgroundColor #FFFFFF
node "Linux 服务器（Docker Compose）" {
  [Nginx :80\n静态资源 + /api 反代] as nginx
  [backend :8080\nSpring Boot jar] as app
  database "MySQL :3306" as mysql
  database "Redis :6379" as redis
  [MinIO :9000/9001] as minio
}
cloud "第三方大模型 API" as llm
[H5 患者端浏览器] as h5
[医生端浏览器] as web

h5 --> nginx
web --> nginx
nginx --> app
app --> mysql
app --> redis
app --> minio
app --> llm
@enduml
```

| 项 | 约定 |
|---|---|
| 后端端口 | 本地 `9003`，`server.servlet.context-path = /stableanginaapi`；容器内统一 `8080` |
| 容器命名 | `stable-angina-mysql`（库 `stable_angina`）/ `stable-angina-redis` / `stable-angina-minio` / `stable-angina-api` / `stable-angina-nginx` |
| compose 工程名 | `name: stable-angina-dev`；`api`、`nginx` 加 `profiles: ["app"]`，日常只起 mysql/redis/minio 时不必带 `--profile app` |
| 镜像 | `deploy/Dockerfile.sa-admin`：`eclipse-temurin:21-jre`，`ARG JAR_FILE=backend/sa-admin/target/sa-admin.jar`，`ENV JAVA_OPTS="-XX:MaxRAMPercentage=75.0"` |
| 配置 | `application-local.yml`（127.0.0.1 + 明文，仅开发）/ `application-prod.yml`（容器内固定值，可被 docker-compose 环境变量覆盖） |
| nginx | 三段：`/stableanginaapi/` 反代后端（含 `/api/files/{id}/url` 换取预签名）；`/admin/`、`/patient/` 托管前端静态。文件内容由浏览器直连 MinIO 预签名 URL，不经 nginx |
| 健康检查 | mysql `mysqladmin ping`、redis `redis-cli ping`，`depends_on: condition: service_healthy` |
| 数据卷 | `stable_angina_mysql_data` / `stable_angina_redis_data` / `stable_angina_minio_data` |

- `docker-compose.yml` 编排 mysql / redis / minio / api / nginx；数据卷持久化，`healthcheck` + `condition: service_healthy` 保证启动顺序；
- 配置：`application-prod.yml` 写固定值（数据库密码、Redis 密码、MinIO 密钥），同名环境变量可覆盖；
- **大模型 API Key 不入配置文件**，走 `sys_config` 加密存储（符合《需求》§4.4）；
- 首次启动由 Flyway 自动建表（`V1~V7`），无需手工导入 SQL。
